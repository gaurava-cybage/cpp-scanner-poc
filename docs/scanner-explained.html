C++ Scanner: how it works

The scanner reads a Visual Studio C++ solution without changing it and writes down its structure: parts, dependencies, calls in order, and database and network use. The result is one file, facts.json, that an AI tool can turn into diagrams.

1. The libraries we use

The product is one Java 17 program with three runtime libraries. Everything else is either Java's own standard library or a Windows tool the program calls.

runtime

libclang (LLVM / Clang)

org.bytedeco:llvm-platform 22.1.8-1.5.14

The C/C++ parser behind the Clang compiler. It reads each file the way a compiler does and gives back the code's structure: classes, functions, calls, the tokens of an expression, and any errors. This is the core of the scanner.

runtime

JavaCPP

bundled with llvm-platform

The bridge that lets Java call libclang's C functions. It is part of the same package, so no separate install is needed.

runtime

Jackson (databind)

com.fasterxml.jackson.core 2.16.1

Reads the JSON that Visual Studio's build tool returns, and writes facts.json in the same layout and formatting as the reference file.

tests only

JUnit 5

5.10.1

Runs the automated tests on every build. It is not part of what the scanner does on a real solution.

Java standard library

Java 17

OpenJDK 17.0.21

Reads files and folders, runs regular expressions over the solution file, reads the project XML with its built-in DOM parser (no extra library), and starts the build tool as a separate process.

external tool

MSBuild and vswhere

MSBuild 18.10.1 (needs 17.8 or later)

Visual Studio's own project reader. The scanner asks it, read-only, for each project's source list, settings and references. MSBuild does not compile anything in this mode. vswhere finds MSBuild when the scan is not run from a Developer prompt.

Analysed by the scanner, not used by it

The scanner recognises calls to two libraries that the sample product uses. It does not link to them.

  • SQLite (sqlite3.h): every call is recorded with its SQL, operation and tables. The header comes from the target machine. The sample uses a stub.
  • Winsock 2 (winsock2.h): every call is recorded; calls for connecting, listening, sending and receiving get a role.
  • vcpkg: only the vcpkg.json file is read, for library versions.

2. The big picture

Six steps run in order, from the solution file to the output files.

3. First step to last step

  1. Read the solution file. The scanner finds every project listed in the .sln file (SolutionParser, a text match on the project lines).
  2. Ask MSBuild about each project. One read-only call per .vcxproj returns the source files with their settings, the project references and the project type. This is the only step that needs Visual Studio installed.
  3. Work out the dependencies. The scanner combines the project references, the link settings in the project file, #pragma comment(lib) lines in the source, and vcpkg.json versions (see section 4).
  4. Parse every source file with libclang. Each file is read with the settings MSBuild gave for it (section 6). Each parsed file is handed to the extractor before it is released.
  5. Extract the facts. From each file: classes and their bases, functions, calls with order and conditions, exits (return and throw), and database and network calls checked against the rules.
  6. Apply the database and network rules. The SQL text is resolved where it is a literal or a simple constant. The SQL files in the solution are read for table definitions.
  7. Build the output. Duplicates are removed, lists are sorted, and facts.json is written. Then one flow file is written for each program entry point, and the two review files are written.

Last step: the review files are written and the console prints the timing summary. Nothing in the solution is ever changed.

4. How dependencies are detected: the files read

A dependency means "this project needs that one or that library". Four sources are combined. Each one is recorded with where it came from, so a reviewer can trace it.

5. What the parser takes as input

libclang needs to be told how each file is compiled, or it would misread the code. For every source file the scanner builds a list of arguments from the MSBuild answer:

ArgumentComes fromWhy it matters
File pathThe file's full path in the solutionOutput refers to files by their path under the solution folder
Compiler mode (cl, Microsoft-compatible)Always setReads the code the way Visual Studio's compiler does
Preprocessor definitions (/D)Project settingsChanges which code exists (for example, WIN32)
Include folders (/I)Project settings, resolved to real foldersLets the parser find headers. Folders that do not exist are skipped
Language version (/std:)Project settingsC++14, C++17 or C++20 rules
Exception handling and runtime libraryProject settingsCorrect reading of try/catch code
Precompiled header and forced includes (/FI)Project settingsBrings in the header the code relies on (for example pch.h)
32-bit flag (-m32)Platform Win32 onlyMatches 32-bit builds

Parsing runs with two options: keep reading after a fatal error (so one missing header does not hide the rest of the file), and include detailed preprocessing information (so macros can be traced back to their use).

6. Parallel or one at a time?

Today: one at a time. The scanner asks MSBuild about the projects in turn, then parses the files in turn. On the sample, parsing averages about 1.7 seconds per file, and the whole scan takes about 40 seconds.

Possible later: libclang can parse separate files in parallel, so the parsing step could run on several cores. The extracted facts would then need to be merged in a fixed order to keep the output identical between runs. This is not built, and it was not needed for the 20-file sample.

8. What the scanner skips, and why

Skipping keeps the output about the product's own design rather than the platform.

SkippedReason
Files other than C/C++Out of scope by design
Windows and compiler system codeDescribes the platform, not the product. The few calls that matter are kept (network, background threads)
Third-party code outside the solution folderOtherwise every external library would appear as part of the product. Calls into it are still recorded
Include folders that do not existListed on screen, then skipped
Compiler-generated constructors and copy operatorsNobody wrote them, so they are not design decisions
Calls to local lambdasCounted inside the enclosing function instead
Repeated code seen in several filesRecorded once, identified by its unique name
Logging, getters and setters, standard library callsLeft out of the flow files only, to keep the business flow readable. Background-thread starts are kept in the flow
SQL that cannot be readMarked <dynamic>. The scanner never guesses SQL

9. What happens when something goes wrong

SituationWhat the scanner doesEffect
A header is missing (for example sqlite3.h)Keeps reading the file and records the errorThe file is analysed; calls to that library are missing. Listed as a diagnostic
libclang cannot produce a result for a fileDrops that file and records whyThat file is missing; the rest is analysed
MSBuild not found, or fails on a projectStops with an error message and exit code 1No output is written. Fix the environment and rerun
SQL or database path built at run timeMarked <dynamic>Still listed, so a developer can check it
Unknown project typeMarked as "unclear"A developer must decide what it is
Code that does not compile on this machineThe scan continuesFewer files count as clean; the reason is printed

In short: one broken file never stops the scan. A broken solution does, and says so.

10. Business decisions

Decisions already made (in the proof of concept)

Read only. The product is never built, compiled, cleaned or changed.
Never guess. Unreadable SQL is shown as <dynamic>, so the result can be trusted where it is stated.
Keep going after errors. Partial results with listed gaps are preferred over no results.
Same output every run. The only differences between runs are the timestamp and scan time.
Windows and Visual Studio only. The project files are read with Visual Studio's own tool, so the scan is tied to that environment.

Decisions still open (for the team)

  1. Should background threads be followed? Today the main flow stops where a thread starts, so the business logic inside the thread is missing.
  2. Should the network helper header count? Some network calls (getaddrinfo) come from ws2tcpip.h and are currently not recorded.
  3. Should SQL passed through a helper function be followed? Some transaction commands go through a wrapper, so they show as dynamic.
  4. Which real solution, settings and header folders should the target run use? Only the sample has been run.
  5. Should the scanner support other database libraries? Only SQLite is understood today.
  6. Should parsing run in parallel? Not needed for 20 files; a decision for a larger target.

12. Suggested slides for management

  1. The problem. Nobody can see quickly how the C++ system fits together: who calls whom, where the data goes, and where the network is used.
  2. What it does. It reads the code without changing it and writes a map of the system. Use section 2 as the picture.
  3. How it works. Three libraries, one Visual Studio query, seven steps. Use sections 1 and 3.
  4. What it found. The numbers from section 11, plus one example flow, drawn from flows/MAIN-App.json.
  5. How far to trust it. The skips and errors (sections 8 and 9), the limits, and the review still to come.
  6. What we need. The open decisions in section 10, a run on the real target, and a date for the developer review.
